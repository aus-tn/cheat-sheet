Variables & operation names

Variables keep values out of the query text, so the same query can be reused and the server can check every value's type. Naming the operation helps with logs and debugging.

query GetProduct($id: ID!, $currency: Currency = USD) {Declare variables with their types and defaults
product(id: $id) {
title
price(currency: $currency)Use a variable as an argument
}
}
{ "id": "42", "currency": "EUR" }The variables, sent as JSON beside the query

Aliases & fragments

An alias renames a field in the response, which lets you ask for the same field twice with different arguments. A fragment is a named, reusable set of fields for one type.

query {
hats: products(first: 3, category: HATS) { totalCount }Alias: the result is under hats
shoes: products(first: 3, category: SHOES) { totalCount }
}
fragment ProductCard on Product {Fields to reuse wherever a Product appears
id
title
price
}
query {
product(id: "42") { ...ProductCard inStock }Spread the fragment with ...
}

Directives

Directives adjust how a query runs. The built-in @include and @skip turn fields on or off with a variable, so one query can serve several screens.

query Product($id: ID!, $full: Boolean!) {
product(id: $id) {
title
reviews @include(if: $full) { rating }Only when $full is true
tags @skip(if: $full)Left out when $full is true
}
}

Mutations

Mutations change data and then return fields, just like a query. When one request has several mutation fields, they run one at a time in order; query fields can run in parallel.

mutation AddToCart($input: AddToCartInput!) {Input objects bundle the arguments
addToCart(input: $input) {
cart { id totalQuantity }Ask for whatever changed
errors { field message }Many APIs return validation problems as data
}
}
mutation {
first: addToCart(input: { productId: "1" }) { cart { id } }Runs first
second: addToCart(input: { productId: "2" }) { cart { id } }Then this one
}
{ "input": { "productId": "42", "quantity": 2 } }

Subscriptions

A subscription keeps a connection open and receives a new result each time an event happens. How it's delivered, often WebSockets or server-sent events, depends on the server.

Pagination

Many APIs page through lists with cursor connections, a convention from Relay rather than part of the spec. Ask for a page, then pass the last cursor back to get the next one.

query Page($after: String) {
products(first: 20, after: $after) {First: page size; after: where to continue
edges {
cursorThis item's position in the list
node { id title }The item itself
}
pageInfo {
hasNextPageKeep going while this is true
endCursorSend it as $after for the next page
}
}
}

Introspection

A GraphQL API can describe itself. Introspection queries are how editors, GraphiQL and code generators learn the schema; some APIs turn it off in production.

{ __schema { types { name kind } } }Every type in the schema
{ __type(name: "Product") { fields { name type { name kind } } } }One type's fields
{ product(id: "42") { __typename } }The type name of any object

Sending requests

Most GraphQL APIs take a POST to one endpoint with a JSON body. The query is sent as a string, with variables and the operation name beside it.

Responses & errors

A response can hold data and errors at the same time. A field that fails becomes null and gets an entry in errors; if that field is non-null, the null moves up to the nearest parent that allows it.

{
"data": {Same shape as the query
"product": { "title": "Hat", "reviews": null }
},
"errors": [{Only present when something went wrong
"message": "Not authorized",
"locations": [{ "line": 4, "column": 5 }],Where in the query
"path": ["product", "reviews"]Which field failed
}],
"extensions": { }Extra server-specific details, like query cost
}
